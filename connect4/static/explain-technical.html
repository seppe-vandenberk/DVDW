01 / THE WHOLE SYSTEM

Practice and visitor play run side by side.

The API process owns two sets of weights. A background thread changes the candidate. Physical games and browser exhibitions use the published network. Publication replaces serving weights only after a promotion check.

These run in separate threads within one API process, not separate training and inference servers. They can still compete for CPU/GPU time. The Play page hosts human games; the debug console's training sample comes from actual background practice.

02 / WHAT THE MODEL ACTUALLY IS

One shared feature extractor, two different predictions.

The model is a convolutional neural network with 154,664 learned numbers. It has no words, prompts, or chat history. It takes a board and produces move preferences and a position estimate.

The board is always “my turn”

API labels stay fixed: the first player is +1, the second −1. Before inference, the board is multiplied by the acting player's sign. Own discs therefore always become +1. This shares knowledge between colors.

Three binary planes then separate own discs, opposing discs, and empty cells. The empty plane is not a legal-move or landing-cell plane. Full columns are excluded separately at policy softmax and in search.

What the heads mean

Policy: “Which moves look promising?” Seven logits become a distribution over legal columns. A 40% prior means preference, not a 40% chance of winning.

Value: “How good is this position for the player to move?” It predicts a discounted signed outcome. Zero can reflect uncertainty, a draw, or balanced evidence; it is not a calibrated 50% win probability.

03 / HOW REPETITION CHANGES THE NETWORK

The AI generates examples, then learns to fit them.

A practice batch runs 16 independent games by default. The candidate plays against recent published networks, the rule opponent, or random play. Only positions where the candidate acts are stored as training examples. The opponent's chosen moves are not copied as expert labels.

Why search targets help

A win/loss says how the game ended. Search adds a richer target at every candidate turn: a seven-column distribution describing which futures were explored most. The policy learns to reproduce these search preferences; the value learns from actual outcomes. No rule-teacher demonstrations pretrain the current default model.

Training uses root Dirichlet noise: 75% network prior plus 25% noise, with concentration 0.3. For the first ten total game plies, it samples actions from visit counts. Later it chooses the highest visit count. This gives practice some variety.

What remains in memory

Replay keeps up to 100,000 simulated positions and 10,000 external positions. A minibatch reserves up to 20% for external experience when sufficient simulated replay is available. If simulated replay is scarce, external samples can fill more of the batch.

The optimizer is AdamW, learning rate 0.001 and weight decay 0.0001. Gradients are clipped to norm 5. The current schedule takes one optimizer step per completed game in a batch, after replay warmup.

04 / WHY QUICK WINS AND SLOW LOSSES MATTER

One result, discounted back through the game.

When a game finishes, each saved position receives +1 if its acting player won, −1 if that player lost, or 0 for a draw. Discounting makes distant outcomes smaller in magnitude.

z = outcome × 0.997remaining plies

A ply is one disc placement, by either player. For this training target, remaining plies is the final action's ply index minus the saved action's ply index. An immediate winning action has a +1 target; an action ten further plies from a win has about +0.970.

Illustrative target values, not a live model prediction. Every discounted win stays positive and every discounted loss stays negative.

There is no per-disc penalty, pair bonus, or center reward in this learner. The old DQN's per-disc reward formula does not describe the current engine.

05 / HOW A MOVE IS CHOSEN

The network suggests. Search investigates.

For visitor play, the published network is placed inside a Monte Carlo tree search. The default budget is 64 simulations per requested move, versus 32 during background practice and evaluation. A simulation follows one path through a tree; it is not necessarily a complete game rollout.

select a = argmax [ −γ Q(child) + 1.5 × P(a) × √(N(parent) + 1) / (1 + N(child)) ]

What this formula balances

Q is the child's average backed-up value from the child's player perspective, so the parent negates it. P is the network's prior preference for that move. N is the visit count. The exploration term favors promising actions that have not yet been examined much.

Search discovers immediate wins and losses by applying the rules. A leaf reached after the opponent has just won has value −1 for the player now due to move; backup flips that sign. The bitboard game engine determines these terminal facts exactly.

One batched call, multiple game trees

Background search collects a leaf from each active independent game tree, then evaluates those leaves in one network batch. Each tree gets its own policy, values, legal moves, and outcome. Batching improves throughput without mixing one game's history with another's.

During visitor inference there is no root noise and no exploratory sampling. The model chooses the action with the highest visit count, breaking exact ties by column order. Search is bounded, so it can still overlook a deeper tactic.

06 / LEARNING DOES NOT IMMEDIATELY REPLACE THE VISITOR AI

A candidate earns its way into visitor play.

The candidate changes after each optimizer step. About every five minutes, once training has begun, the worker freezes its progress while it runs evaluation. The API can continue serving the published network.

Score is (wins + 0.5 × draws) / games. Evaluation uses the training search budget, equal first/second-player games, and two seeded opening plies. Rule/random opening seeds stay fixed for comparison; promotion-opening seeds vary with optimizer updates. A separate rehearsal evaluates final models with different seeds against random, rules, and depth-four alpha-beta search.

A passing gate is a practical selection rule, not proof of universal improvement. A game may span generations if publication happens between turns; game histories remain valid because the rules do not change. The debug chart includes candidates that failed promotion, so its latest candidate score may differ from the visitor model's strength.

07 / HOW A PHYSICAL GAME BECOMES EXPERIENCE

The camera must confirm what really happened.

A move request predicts a placement. It is not evidence that the robot actually placed the disc. Each physical game has a unique game ID, allowing many games and background learning to coexist while keeping action order inside each game.

Only the AI's saved positions and search distributions enter external replay; the human's move is an opponent reply. /finish assigns the outcome, even if the human won. Identical move/finish retries do not duplicate actions or experience within an active session, but the robot controller must separately prevent a second physical placement on retry.

Published and learner checkpoints save separately. Learner state includes replay and optimizer state; active game sessions and queued unsaved results are not crash-proof. The debug console shows pending confirmations, external episode counts, queue depth, and both checkpoint timestamps.
